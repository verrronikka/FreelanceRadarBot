FreelanceRadar
Архитектура и техническое задание MVP
Документ переводит бизнес-гипотезу в реализуемый план: Telegram-бот отслеживает новые заказы на разрешённых источниках, сопоставляет их с профилями пользователей и отправляет подходящие уведомления. Цель MVP — проверить ценность скорости и релевантности, а не построить универсальный агрегатор.
Решение и границы
Рекомендуемая реализация — модульный монолит на Python: Aiogram 3, PostgreSQL, Redis и Celery. Такой состав покрывает фоновые опросы и доставку уведомлений без преждевременного выделения микросервисов. HTTP-интеграции с площадками допускаются только через официальные API, RSS или источники, чьи условия использования разрешают автоматизированное чтение.
В MVP входит	За пределами MVP
Подключение 1–2 разрешённых источников через адаптеры	Обход CAPTCHA, антибот-защит, приватных API и ограничений площадок
Настройка бюджета, ключевых слов, исключений и профиля	Отклик от имени пользователя, хранение паролей или токенов бирж
ИИ-оценка релевантности по явному согласию	Биллинг, подписки, реферальная программа, веб-кабинет
Telegram-уведомление со ссылкой на исходный заказ	Сложные рекомендации, обучение модели, мультиаккаунтность
Допущения для разработки
•	Перечень источников утверждается до Sprint 2 после юридической и технической проверки каждого источника.
•	Целевой SLA доставки — до 60 секунд от момента, когда заказ доступен выбранному интеграционному каналу. Это не обещание появления заказа раньше, чем его отдаёт источник.
•	ИИ-фильтр включается пользователем отдельно; без него работает детерминированный фильтр по бюджету и ключевым словам.
1  Декомпозиция бизнес требований
1.1  Проверка MVP
Функция MVP	Системное действие	Результат для пользователя	Критерий готовности
Сбор новых заказов	Адаптер запрашивает источник, нормализует заказ, устраняет дубликаты	Новые заказы попадают в очередь обработки	Не менее 95% доступных тестовых записей сохраняются без дублей
Настройка фильтров	Бот валидирует профиль и сохраняет версию правил	Пользователь управляет релевантностью в Telegram	Изменение действует на следующий цикл обработки
Умный фильтр	Сервис формирует структурированный запрос к LLM и получает оценку	Пользователь получает только релевантные предложения	Решение объяснимо: показываются совпавшие признаки
Моментальное уведомление	Очередь создаёт delivery и Telegram API отправляет сообщение	Карточка заказа и кнопка Откликнуться	Повторная доставка при временной ошибке
1.2  Нефункциональные требования
Категория	Требование
Производительность	Команда бота отвечает за ≤ 2 с в p95. Цикл одного источника укладывается в заданный его правилами интервал, но не чаще одного запроса в 30 с без явного разрешения.
Доступность	Фоновые задачи повторяются с экспоненциальной паузой. Ошибка источника не блокирует остальные источники.
Безопасность	Секреты только в переменных окружения/секрет-хранилище. Токены не пишутся в логи. Доступ к БД закрыт из интернета.
Приватность	Храним Telegram ID, настройки и историю доставок. Текст заказа — максимум 30 дней, затем удаление. Удаление профиля очищает персональные настройки в течение 24 ч.
Наблюдаемость	Структурированные логи, метрики: время опроса, число новых заказов, ошибки адаптера, задержка доставки, стоимость LLM.
Нагрузка MVP	До 1 000 активных пользователей, 2 источника, до 10 000 заказов/сутки, до 30 одновременных команд.
1.3  Ограничения
•	Не использовать Selenium как штатный путь интеграции: он хрупок, дорог в поддержке и может нарушать правила источника. Разрешённый fallback — только документированный API/RSS или согласованный экспорт.
•	OpenRouter может быть недоступен, вернуть ошибку или исчерпать лимит; система обязана деградировать к детерминированным правилам и честно указать это в логе, не блокируя уведомление.
•	Лимиты Telegram и источников учитываются очередями, rate limiter и идемпотентностью.
2  Компонентная архитектура
Все компоненты разворачиваются одним Docker Compose проектом на VPS. Внутренние связи — приватная сеть; наружу открыт только исходящий доступ к Telegram, источникам и LLM API.
 
Рисунок 1  Компонентная схема и основной поток данных
Пользователь → Telegram Bot API → Aiogram API
                                  │
              PostgreSQL ← Application service → Redis / Celery
                                  │                     │
             Source adapters ← Polling tasks      Delivery tasks → Telegram
                                  │
                         Allowed source APIs / RSS
                                  │
                         OpenRouter gateway → выбранная LLM-модель
Компонент	Ответственность	Технология
Telegram bot	Команды, пошаговая настройка, карточки, UX состояния	Python 3.12, Aiogram 3
Application service	Валидация профилей, правила, оркестрация use cases	Python, SQLAlchemy, Pydantic
Source adapters	Получение и нормализация данных конкретного источника	HTTP client, RSS client; единый интерфейс Adapter
Worker scheduler	Периодический запуск адаптеров, retry, дедупликация	Celery Beat + Celery workers
Matching service	Детерминированные правила и опциональная LLM оценка	Python; OpenRouter API через gateway
PostgreSQL	Источник истины: пользователи, профили, заказы, решения, доставки	PostgreSQL 16
Redis	Брокер задач, короткие блокировки, rate limiting	Redis 7
2.1  Потоки данных
Сценарий A  Настройка профиля
Шаг	Действие	Проверка и сохранение
1	/start создаёт пользователя и показывает меню	telegram_user_id уникален; нет персональных данных сверх необходимых
2	Пользователь выбирает источники	Разрешаются только active sources
3	Вводит минимальный бюджет и ключевые слова	Бюджет ≥ 0; ≤ 20 ключевых слов; каждое 2–64 символа
4	Опционально вводит описание для ИИ	≤ 1 500 символов; показывается согласие на передачу текста LLM-провайдеру
5	Бот показывает сводку, подтверждает	Профиль и filters сохранены транзакционно; обновлён version
Сценарий B  Новый заказ до уведомления
Шаг	Действие	Гарантия
1	Scheduler запускает poll_source(source_id)	Lease в Redis предотвращает параллельный опрос одного источника
2	Адаптер читает только разрешённый канал и нормализует запись	Валидация обязательных title, url, external_id или stable hash
3	Repository выполняет upsert заказа	Уникальность source_id + external_id; повторный запуск безопасен
4	Matching получает активные профили выбранного источника	Сначала budget/keywords/exclusions; ИИ только для кандидатов
5	Создаётся notification_delivery	Уникальность profile_id + job_id; статус pending
6	Worker отправляет карточку Telegram	Retry на 429/5xx; статус sent или failed с причиной
Сценарий C  Недоступен LLM
Если вызов LLM превысил 8 секунд, вернул ошибку или исчерпан лимит, matching записывает llm_status=unavailable, применяет только детерминированные правила и ставит verdict=matched либо rejected. Пользователь не получает технический текст ошибки; в карточке при matched можно показать «подобрано по фильтрам».
3  Модель данных
users 1 ── * profiles 1 ── * profile_sources * ── 1 sources
profiles 1 ── * filter_rules
sources 1 ── * jobs 1 ── * match_decisions * ── 1 profiles
match_decisions 1 ── 0..1 notification_deliveries
Сущность	Ключевые поля	Правила целостности
users	id UUID, telegram_user_id BIGINT, status, created_at	telegram_user_id UNIQUE NOT NULL; status active|deleted|blocked
profiles	id UUID, user_id, name, min_budget, ai_prompt, ai_enabled, version	user_id FK; min_budget ≥ 0; ai_prompt nullable; version растёт при изменении
sources	id, code, name, status, poll_interval_sec	code UNIQUE; status active|paused; interval ≥ 30
jobs	id UUID, source_id, external_id, url, title, description, budget_min/max, published_at, raw_hash	UNIQUE(source_id, external_id); если external_id нет — stable hash в отдельном поле
filter_rules	id, profile_id, rule_type, value, is_exclusion	rule_type keyword|category; нормализованное value; UNIQUE(profile_id, rule_type, value)
match_decisions	id, profile_id, job_id, verdict, score, reasons, llm_status	UNIQUE(profile_id, job_id); verdict matched|rejected|error
notification_deliveries	id, decision_id, status, attempts, sent_at, error_code	decision_id UNIQUE; status pending|sent|failed|cancelled
4  Контракты и обработка ошибок
4.1  Внутренний контракт адаптера
Каждый адаптер обязан реализовать fetch_new(cursor) → FetchResult. Адаптер не принимает решений о фильтрации и не общается с Telegram.
{
  "source_code": "example_exchange",
  "cursor": "2026-09-20T07:00:00Z",
  "items": [{
    "external_id": "12345", "url": "https://source.example/jobs/12345",
    "title": "Landing page design", "description": "...",
    "budget_min": 20000, "budget_max": 35000,
    "currency": "RUB", "published_at": "2026-09-20T07:01:03Z"
  }],
  "next_cursor": "2026-09-20T07:01:03Z"
}
Ситуация	Действие системы	Код / сообщение для логов
400 или невалидный ответ источника	Не ретраить автоматически; создать alert, не менять cursor	SOURCE_SCHEMA_INVALID
401/403	Остановить адаптер источника до ручной проверки прав	SOURCE_ACCESS_DENIED
429	Retry after header или экспоненциальная пауза; не превышать лимит	SOURCE_RATE_LIMITED
5xx или timeout	До 3 повторов; затем задача failed, следующий плановый цикл продолжается	SOURCE_TEMPORARY_FAILURE
Дубликат заказа	Не считать ошибкой, upsert обновляет observed_at	JOB_DUPLICATE
Telegram 429	Отложить доставку согласно retry_after	TELEGRAM_RATE_LIMITED
4.2  Контракт LLM gateway
В gateway передаётся только текст профиля, нормализованная карточка заказа и версия промпта. Ответ строго валидируется Pydantic-схемой; произвольный текст не используется для решения.
request: {"profile": "Делаю лендинги на Tilda", "job": {"title": "...", "description": "...", "budget_min": 20000}, "prompt_version": "v1"}
response: {"match": true, "score": 0.86, "reasons": ["Tilda", "бюджет выше минимума"], "model": "configured-model"}
Ошибка API клиента	HTTP	Тело ответа
Некорректная команда или настройки	400	{"error":{"code":"VALIDATION_ERROR","message":"Проверьте значение бюджета"}}
Пользователь не найден / удалён	404	{"error":{"code":"USER_NOT_FOUND","message":"Профиль недоступен"}}
Временная недоступность	503	{"error":{"code":"TEMPORARY_UNAVAILABLE","message":"Попробуйте позже"}}
4.3  Конфигурация
Переменная	Назначение	Правило
TELEGRAM_BOT_TOKEN	Токен бота	Только secret store; не логировать
DATABASE_URL, REDIS_URL	Внутренние подключения	TLS где доступно; не публиковать наружу
OPENROUTER_API_KEY, OPENROUTER_BASE_URL, LLM_MODEL	OpenRouter, endpoint и выбранная модель	Ключ — только в secret store; модель меняется без правки кода
SOURCE_*_BASE_URL, SOURCE_*_TOKEN	Настройки разрешённого адаптера	Отдельно на источник; токены секретны
POLL_INTERVAL_SECONDS, LLM_TIMEOUT_SECONDS	Эксплуатационные параметры	В environment; допустимые диапазоны валидируются при старте
5  Алгоритм сопоставления
Этап	Логика	Выход
Нормализация	HTML → plain text; Unicode NFC; пробелы; currency/budget в числовой вид. Не изменять исходный raw payload.	NormalizedJob
Быстрый отсев	Источник включён; бюджет не ниже профиля; не найдено исключающих ключевых слов.	candidate или rejected + reason
Ключевые слова	Совпадение по title + description. Для профиля без ключевых слов этап пропускается.	score_rules, reasons
LLM оценка	Только ai_enabled и candidate. Модель возвращает JSON по фиксированной схеме.	score_llm, reasons, llm_status
Решение	matched, если score ≥ 0.70; иначе rejected. При LLM error используется score_rules.	MatchDecision
Доставка	Карточка: заголовок, бюджет, источник, 1–2 причины, кнопка Откликнуться → исходный URL.	NotificationDelivery

8  Приемка и передача
Проверка	Критерий
Функции MVP	Все три core-функции демонстрируются на тестовых данных и одном разрешённом источнике.
Скорость	В тесте от появления записи в доступном источнике до создания delivery проходит ≤ 60 с при нормальной работе внешних API.
Надёжность	Повторный poll не создаёт дубликат; Telegram 429 и временная ошибка источника корректно ретраятся.
Безопасность	Секреты отсутствуют в репозитории и логах; удаление пользователя работает.
Границы	Нет автоматического отклика, нет запрещённых интеграций и обхода защит.
Передача	Разработчику переданы .env.example, схема миграций, список источников с подтверждёнными правилами, runbook и доступы.
Открытое решение перед началом Sprint 2: утвердить конкретные источники и для каждого зафиксировать URL документации/API, лимиты, разрешённый интервал опроса и владельца доступа. Без этой записи адаптер не разрабатывается.
